# .claude/ — このリポジトリのセッション設定

## セッション肥大化ガード（有効・自動）

`settings.json` の `UserPromptSubmit` フックが、プロンプト送信のたびに
`hooks/session-size-guard.sh` を呼び、セッションが一定の長さを超えたら警告を出します。

**なぜ要るか**（2026-08-17 公式ドキュメントで裏取り・訂正）:
1セッションが伸びるほど、毎ターンの **cache_read**（コンテキスト再読込、0.1倍課金）が
積み上がります。これが主因です。cache_write 自体は通常ターンでは新規追加分のみで
ほぼ一定ですが、モデル切替・エフォート変更・fast mode切替・plugin/MCP接続変更・
compact直後・1時間の空白後の再開などでキャッシュが丸ごと無効化されると、蓄積した
全文脈が（サブスクの1時間TTL時）2倍課金で一括再書き込みされます。セッションが
伸びるほど、この「無効化時の一括再書き込み」の被弾範囲（exposure）も大きくなります。
詳細: [How Claude Code uses prompt caching](https://code.claude.com/docs/en/prompt-caching)

旧版はここで「cache_write が（セッションが伸びるほど）積み上がる」と書いていましたが
不正確でした。積み上がるのは cache_read で、cache_write は通常ターンでは一定、
無効化時にのみスパイクします。「長いセッションほど高くつくリスクが増す」という
結論自体は今回の裏取りでも支持されますが、機序の説明を訂正します。

[要確認] プラン内（5時間ローリング上限以内）の通常利用で、これらの倍率がどう
「クレジット消費」に反映されるかは公式ドキュメントに明記がありません。明言されて
いるのは「プランの利用上限を超えて usage credits を使う場合は、その分は課金される」
ことだけです。上限内の通常消費にも同じ倍率が内部的に使われているかは未確認です。

消費分析では、最も重かった1セッションだけで計測分の約41%を占めていました。
[要確認] この数値は別セッションの分析に基づくもので、今回は再検証していません。

**新知見**: サブエージェント（Task/Agent ツール経由）は、サブスクでも常に **5分TTL**
でキャッシュされます。自動延長される1時間TTLはメインの会話にのみ適用されます。
間隔の空くサブエージェント呼び出しを多用すると、1時間TTLの恩恵を受けられず
キャッシュの再書き込みが増える可能性があります。

**指標は2段構え**です。

① **直近ターンの `cache_read_input_tokens`** — 毎ターン読み直しているコンテキスト量そのもの。
transcript の `message.usage` から取得します。**これが本命**で、行数よりはるかに実態に近い数字です。

② ①が取れなければ **エントリ数（行数）** へフォールバック。

| 指標 | 警告 | 強い警告 |
|---|---|---|
| ① cache_read トークン | 400,000 以上 | 700,000 以上 |
| ② エントリ数（①が取れない場合） | 300 以上 | 600 以上 |
| いずれも閾値未満／情報が取れない | 完全に無音 | — |

**ブロックはしません。** 作業を止めるのは壊れる側なので、警告のみです。
`transcript_path` が取れない・ファイルが無い・JSONが壊れている場合はすべて黙って通します。

**閾値の調整**:

```sh
export CLAUDE_SESSION_WARN_CTX_TOKENS=500000
export CLAUDE_SESSION_LOUD_CTX_TOKENS=800000
export CLAUDE_SESSION_WARN_ENTRIES=400   # フォールバック側
export CLAUDE_SESSION_LOUD_ENTRIES=800
```

**設計上の注意 — なぜ2段構えか**: ①は transcript の内部形式に依存します。公式ドキュメントは
「エントリ形式は内部仕様でバージョン間で変わる。直接パースするスクリプトは壊れる」と
明記しているため、**①が壊れたら黙って②へ落ちる**構造にしてあります。②は `wc -l` だけなので
形式変更に強く、最後の砦として残ります。

**実測の較正データ**: このフックを作ったセッションは **420エントリ / cache_read 約72万トークン**
でした。つまり毎ターン72万トークンを読み直していた計算です。既定値はここから置いた暫定値なので、
実際の表示を見て調整してください。

## コンテキスト使用率とキャッシュ効率の常時表示（任意・未接続）

`statusline.sh` は現在のコンテキスト使用率をバーで表示し、あわせて直近ターンの
cache_read / cache_write トークン数も表示します。
**セッションが膨らむ根本原因は「膨らんでいることが見えない」こと**なので、
閾値で鳴るフックより、常に見えるこちらのほうが効く可能性があります。

**これは思いつきではなく公式推奨手法です**: 公式ドキュメントは「キャッシュ性能を
確認する最も直接的な方法は、`current_usage` を読む statusline スクリプト」と
明記しています。
詳細: [Check cache performance](https://code.claude.com/docs/en/prompt-caching#check-cache-performance)

既定では接続していません。プロジェクト設定に置くと個人の statusline を
上書きしてしまうためです。使う場合は `~/.claude/settings.json` に自分で:

```json
{
  "statusLine": {
    "type": "command",
    "command": "/絶対パス/my-project/.claude/statusline.sh"
  }
}
```

表示例: `ctx [#######...] 74% | cache w:1K r:340K`
（70%以上で `ctx!` に変わります。`current_usage` はセッション開始直後や `/compact`
直後は null になるため、その間は cache 欄を省略しコンテキストバーのみ表示します）

## 破壊的git操作の拒否（有効・自動）

`settings.json` の `permissions.deny` が、`git reset --hard` / `git push --force`・`-f` /
`git clean -f*` を無条件でブロックします。claude-backup・second-brain が持つ「データを
失わない」という不変条件が、これまで CLAUDE.md の「退避・確認する」という**モデルの
判断任せ**でしか担保されていなかったため、強制層へ格上げしました。

**なぜ Hook ではなく Permission か**（公式ドキュメントで裏取り済み）:
最初は PreToolUse Hook でブロックする案を検討しましたが、公式ドキュメントに
「ハードな許可・拒否を強制したいなら Hook でなく permission システムを使うべき」
(`hooks` ドキュメント: *"use the permission system rather than a hook to enforce a
hard allow or deny"*) と明記されており、さらに `permissions` ドキュメントには
「PreToolUse Hook が何を返しても、deny/ask ルールは無関係に評価される」ともあります。
Hook を主軸にする設計は公式ガイダンスと逆行するため、`permissions.deny` のみで実装し
直しました。

**`rm -rf` を対象に含めていない理由**: `permissions.deny` は例外（allowlist）を持てない
仕様のため、`rm -rf` を対象にすると、このセッション自身が使うスクラッチディレクトリの
一時ファイル削除まで一律ブロックされ、業務が止まります。したがって `rm -rf` は今回の
対象から意図的に外しています。**このリポジトリで最も破壊力の大きい操作に対する物理的な
防御は、依然として存在しません。** CLAUDE.md の「壊れない側に倒す」という運用規律への
依存が、この一点だけ残っています。

**リモートセッションへの到達性**: 上記「リモートセッション（claude.ai / モバイル）での
動作」の検証により、`~/.claude/settings.json`（個人設定）はリモートに届かず、リポジトリ
側の `.claude/settings.json` だけが唯一の経路であることは既に実測済みです。本ルールも
同じ経路で配布されるため、追加の検証なしにリモートセッションへも及びます。

[要確認] `permissions.deny` が複合コマンド（`&&`・`;`・`$()` によるコマンド置換）を
どこまで検出するかは、公式ドキュメントで直接の明記を確認できていません。したがって
「通常の誤操作は止めるが、意図的な迂回を完全に防ぐものではない」という前提で運用して
ください。

## 他リポジトリへの配布（`install-to.sh`）

リモートには個人設定が届かないため、カバーしたいリポジトリごとに `.claude/` の配置が要ります。
つまり複製が生じ、**複製は必ずドリフトします**。手でコピーせず、このスクリプトを使ってください。

```sh
bash .claude/install-to.sh ../gas-backup
```

- **このリポジトリの `.claude/` が正本**です。更新はここで行い、導入先では再実行して同期します
- **冪等** — 何度実行しても重複登録されません
- 既存の `settings.json` は**破壊しません**。フック配列に追記マージするだけで、
  既存の `permissions` や他のフックはそのまま残ります（上書き前に `.bak` を作成）
- 不正なJSONの `settings.json` を見つけたら中断します（壊さないため）
- 導入先に `SOURCE.md` を置き、直接編集しないよう明記します

配布先の優先順位は消費実態から: **gas-backup**（最重量セッションを含む）→ **cybozu-inhouse**。
実行後は導入先で `git diff` を確認してからコミットしてください。

**実行結果(2026-08-18)**:
- リモートセッションの GitHub スコープは `suhara-gif/my-project` のみで、他リポジトリへは
  `add_repo` 相当の手段がこのセッションには無く、直接の配布は実行不可能でした(実測で確認)。
  代わりにユーザーがローカル環境で `install-to.sh` を実行する形で配布しました。
- **gas-backup**: 問題なく導入・コミット・push 済み。
- **cybozu-inhouse**: `.gitignore` が `/*` で全部無視し、`!cybozu-replacement/` 等
  5つの Cybozu 内製化ディレクトリだけを許可リストに載せる設計(コメント:
  「~/gas には他プロジェクトが同居しており、巻き込まない」)。`.claude/` はこの許可リストに
  無いため、除外されていました。

  最初は「このリポジトリの意図的なスコープ外」と判断し配布見送りを提案しましたが、
  第三者レビューで根拠不足と判定して撤回しました。理由:
  - `.gitignore` のコメントが名指ししているのは「他の *プロジェクト*」(watchtower 等)であり、
    Claude Code のセッション設定(ツール構成)を同列に扱うと明記されているわけではない
    ([要確認] だった点 — 断定していたのは推測の飛躍)
  - リポジトリ横断の秘密除外パターン(`.env`・`*.pem`・`credentials*.json` 等)はディレクトリを
    問わず効くため、`.claude/` を許可リストに加えても秘密漏えいの実害は増えない
  - 配布そのものの目的(リモートセッションへのガード到達)を考えると、除外したままでは
    cybozu-inhouse 上のリモートセッションだけ無防備になる

  最終判断: `.gitignore` に既存の書式(`!cybozu-replacement/` 等)と揃えて
  `!.claude/` を1行追加し、`.claude/` 全体を許可リストに含める。ディレクトリ単位の
  許可は他5エントリと同じリスク水準で、秘密除外は前述の通り別レイヤーで効く。

  [要確認] ユーザーが実際に cybozu-inhouse に対してリモート(クラウド)セッションを使うかは
  未確認です。ローカル専用なら、コミットしなくてもローカルの `.claude/` はそのまま動作する
  ため急ぐ必要はありません。逆にリモートを使うなら、コミットしないと保護が効きません。

## 個人設定として推奨（このリポジトリには入れていません）

消費の 82〜92% が Opus に乗っていたため、既定モデルを下げるのが最大の打ち手です。
ただし**モデル選択は個人の裁量**で、プロジェクト設定に書くとこのリポジトリを開いた
全セッションに強制されるため、ここには入れていません。`~/.claude/settings.json` に:

```json
{ "model": "sonnet", "effortLevel": "medium" }
```

Opus が要る作業（設計判断・大規模リファクタ・込み入ったデバッグ）では都度切り替えてください。

[要確認] この施策（モデル選択）とセッション肥大化ガードは、どちらも「クレジット消費を
減らす」を掲げていますが、独立した変数に効いています。セッションを区切ってもモデル比率
（Opus/Sonnet）は変わらず、モデルを下げてもセッション長は変わりません。両方が加算的に
効くのか、片方が支配的でもう片方は補助的なのかは検証していません。

## リモートセッション（claude.ai / モバイル）での動作 — 検証済み

消費の大半はクラウドのリモートセッションです。実際のリモートコンテナ内で確認しました。

| 確認項目 | 結果 |
|---|---|
| transcript は存在するか | ✅ `~/.claude/projects/<project>/<session-id>.jsonl` に実在 |
| UserPromptSubmit フックは動くか | ✅ ハーネス自身が同イベントのフックを使用中 |
| `~/.claude/settings.json` は届くか | ❌ **存在しない**。個人設定はリモートに届かない |
| 本フックは実物の transcript で動くか | ✅ 動作確認済み |

**したがってリポジトリ側の `.claude/settings.json` が、リモートセッションに設定を届ける
唯一の経路です。** これが本フックをプロジェクト設定に置いている理由です。

## 未確認事項

- **閾値の妥当性** — [2026-08-24 実測で追加検証] 1週間後フォローアップの一環として、
  この分析セッション自身の transcript を実測しました。2,062エントリ、cache_read は
  最大757,323トークンに到達(LOUD閾値700Kを実際に超過)。WARN閾値(400K)はセッション
  序盤(全体の約7%地点)で早々に超えており、その後セッション中盤で51K付近まで急落
  (compactまたは同等のリセットが発生したとみられる)、終盤にかけて再び517Kまで
  増加しました。当初の較正データ(420エントリ/約72万トークン)と合わせて2セッション分
  になり、いずれも閾値を実際に超える長さに達しています。閾値を上げる根拠は今のところ
  見当たりません。[要確認のまま] サンプルが長時間セッション2件に偏っており、短時間で
  終わる大多数のセッションでの偽陽性率(閾値を超えるが実際は問題ない場合)は未計測です。
- **`autoCompactWindow` を下げる案は採用していません** — 公式ドキュメントによれば、
  キャッシュが温かい状態での `/compact` は要約対象をキャッシュから読むため
  「文脈量の割に安い」一方、1時間TTLを超える空白の後（＝再開時）の `/compact` は
  全文脈を無キャッシュで再処理するため最も高くつくとされています。
  [出典](https://code.claude.com/docs/en/prompt-caching#compacting-the-conversation)
  「頻繁な自動圧縮が読み直しより安いか」は依然未検証のため、採用は見送っています。
- **PR #40 の消費分析の具体的な数値（41%、Opus比率82〜92%）** — 本リポジトリの
  範囲では再検証していません。元の分析セッションのデータに依存しています。
- **「1週間後に使用状況を確認する」フォローアップ** — 2026-08-17時点でこのリポジトリ
  内には仕組みが存在せず、計画だけが書かれていました。同日、この分析セッション自身に
  1週間後（2026-08-24 UTC）の自己リマインドを送るスケジュールを設定し、この抜け漏れは
  解消しました（`send_later` 使用。ただしこのリマインドは本セッションが有効な間のみ
  届きます）。
