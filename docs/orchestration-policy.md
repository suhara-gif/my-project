# オーケストレーション（並行サブエージェント）の判断基準

CLAUDE.md「計画・設計」から参照される運用規則。**この判断をユーザーに丸投げしない**ために、
チェック可能な条件として置く。判定はこちらが行い、ユーザーには可否だけを聞く。

## 適用範囲

対象は **セッションが `Workflow` / `Agent` ツールを起動するかどうかの判断**だけ。
`second-brain/research.sh` のように**キットのスクリプトが内部で並行化する設計は対象外**
(仕様として並行前提であり、この規則で止めない)。

## 既定

**既定は単一セッションで通す。** 並行化は例外で、下の必須条件を全部満たしたときだけ提案する。

## 必須条件（すべて満たすこと）

- [ ] 各片が**他の片の出力を必要としない**。B の入力に A の結果が要るなら、並行は
      「逐次 + オーバーヘッド」に退化する。**件数ではなく独立性が第一条件。**
- [ ] 各片が**自己完結した指示**として書ける(対象・出力形式が片ごとに閉じている)。
- [ ] 単一セッションで通すとコンテキストに載りきらない量がある。
- [ ] **読み取り中心**の作業である(横断調査・レビュー・広い探索)。

## 向かない作業（満たしていても提案しない）

- **コード変更のファンアウト。** ほとんどのコーディングタスクは共有コンテキストと相互依存を
  必要とするためマルチエージェントに向かない、とされる
  ［要確認：一次情報 anthropic.com/engineering/multi-agent-research-system は本環境の
  egress プロキシで取得できず、二次情報のみで確認］。
  ファイル競合を worktree で分離でき、**かつユーザーの明示要求がある**ときだけ検討する。
- **検証・検品目的。** まず `/up-verify`(`.claude/commands/up-verify.md`)を使う。単一セッションで
  作る係と検品係を分ける方が安く、既にこのリポジトリにある。それで足りない規模のときだけ検討。
- 範囲が既に絞れている作業(1キット内の修正、単一ファイルの調査)。

## 非対話セッションでの扱い

フック・launchd/cron・`claude -p` の子セッションでは、**提案も起動もしない**(単一セッションで通す)。
承認を求める `AskUserQuestion` は `dontAsk` 権限モードで拒否されるため、提案しても待つ相手がいない
(出典: https://code.claude.com/docs/en/headless —「`AskUserQuestion` … are denied even when an
allow rule matches」)。**このリポジトリの実行経路の多くはこちら側**であることに注意する。

## 提案の書式

必須条件を満たしたら、実行前に次を1〜3行で示して可否だけを聞く。
**ユーザーに判定基準を思い出させない。**

1. 何を何片に割るか(分割の軸)。
2. エージェント数と、各片が返すもの。
3. 単一セッション比の規模は「エージェント数 × ラウンド数」の構造で書く。**金額は書かない**
   (`--output-format json` の `total_cost_usd` は実行後の client-side estimate であり、
   事前見積もりには使えない)。

参考値: エージェントはチャットの約4倍、マルチエージェントは約15倍のトークンを使うとされる
［要確認：上と同じ理由で二次情報のみ］。本セッションの既定ガイドラインは
ワークフロー1本あたり15エージェント未満。

## この規則自体の保守

- 判定を誤った実例が出たら `docs/learnings/` に1件足し、上の必須条件を書き換える。
- CLAUDE.md 側はポインタ4行に留める。CLAUDE.md は 200 行以内が自リポジトリの上限で、
  現在196行。**次にルールを足すときはディレクトリ階層での分割が先**(提案は PR #39 本文)。
