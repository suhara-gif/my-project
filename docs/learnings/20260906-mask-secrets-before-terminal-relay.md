# 代理ターミナル操作で秘密情報を含む出力を、宛先を切り替えた瞬間にマスクし忘れた

- 日付: 2026-09-06
- 種別: 失敗した試み / 調査
- 触れたファイル: CLAUDE.md(今回追記)、ユーザー環境: `~/.claude.json`、`~/google-ads-mcp/.env`、`~/google-ads-mcp/meta_credentials.json`

## 問題

Metaアクセストークンの更新作業で、ユーザーのMacの `.env` を代理でnano編集させた後、
トークンが依然「期限切れ」扱いされる原因を切り分けるため、`~/.claude.json` の中身を
`grep -A 15 '"meta' ~/.claude.json` で確認するよう依頼した。このコマンドは秘密情報
(`META_ACCESS_TOKEN` 等)を含む `env` ブロックをそのまま出力する可能性があったが、
マスキングも警告も付けずに提示した。ユーザー自身が「アクセストークン表示されてるけど、
そのまま貼り付けて平気?」と気づいて確認したことで、生トークンの貼り付けを回避できた。

## 文脈

同じ会話の中で、直前まで扱っていた `.env` ファイルについては「文字数だけ報告してもらう」
「全文を貼らないよう明示的に警告する」という慎重な扱いを既に徹底していた。ところが確認対象が
`.env` から `~/.claude.json`(MCPサーバーの起動設定ファイル)に切り替わった瞬間、同じ警戒を
適用できなかった。ファイルの見た目上のラベル(「`.env`=秘密」「`.json`=設定」)で警戒レベルを
判断しており、「認証情報を保持しうるかどうか」という機能的な基準で判断できていなかった。
加えて、実際に `~/.claude.json` の該当MCPサーバー設定は `env: {"META_ACCESS_TOKEN": ""}` と
いう形でトークンを直接保持する設計だったため、一見汎用的な設定ファイルに見えて実際は `.env` と
同じ機微度を持っていた(この設定自体が、`.env` を書き換えてもトークンが反映されなかった
根本原因でもあった: `env` に空文字列としてキーが存在すると、`python-dotenv` の
`load_dotenv()` はデフォルトで既存の環境変数を上書きしないため、`.env` の値が無視され続けていた)。

## 解法と、その理由

- 謝罪と個別のマスキング対応(その場でsed付きコマンドを出し直す)だけで終わらせず、5Whysで
  「なぜ具体ルールとして固定化されていなかったか」まで遡った。
- 根本原因は「秘密情報を含みうる出力は対象を問わず常にマスクする」という恒久ルールが
  リポジトリに存在せず、実行者(モデル)の都度の注意力に依存していたことだった。
- 個別対応の積み重ねだけでは同じ抜けが別の文脈で再発するため、CLAUDE.mdに
  「対象ファイルの見た目」ではなく「機能(認証情報を保持しうるか)」で判断する基準を明文化した。

## うまくいかなかったこと

「`.env` は慎重に扱う」という個別対応はその場では正しく実行できていたが、これを一般化された
ルールとして明文化していなかったため、確認対象が変わった瞬間に同じ注意が再現されなかった。
正しい個別対応をその都度行えていることは、恒久的な再発防止の証拠にはならない。

## 抽出したルール / ヒューリスティック

**秘密情報(トークン・パスワード・APIキー・シークレット)を含みうる出力を代理のターミナル操作で
提示する前は、対象ファイルの拡張子や用途ラベル(`.env`/`.json`/config等)によらず、「このファイル・
コマンド出力は認証情報を保持しうるか」を都度チェックする。該当する場合は、出力を提示する前に
必ずマスキング(`sed`等)するか、実行前に一言警告する。** 判断基準は見た目ではなく「認証情報を
保持する可能性がある機能かどうか」。MCPサーバー設定ファイル(`~/.claude.json`等、`env` ブロックで
トークンを保持しうるもの)はこの基準に該当する典型例として扱う。
