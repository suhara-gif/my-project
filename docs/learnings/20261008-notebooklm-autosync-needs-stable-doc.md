# NotebookLMの自動同期は「同じGoogleドキュメント」の編集にしか効かない。改定が別ファイルで来るなら1つに束ねる

- 日付: 2026-10-08
- 種別: 設計判断
- 触れたファイル: kitei-qa/src/Code.gs, kitei-qa/README.md

## 問題
就業規則を NotebookLM で質問できるようにしていたが、改定のたびに新版を手動でアップロードし直す必要があった。
最初は Claude API で答える Web アプリを作ったが、「API など追加課金なしで」と求められた。

## 文脈
- NotebookLM は2026年5月から、Googleドキュメント・スプレッドシート・スライドのソースについて、Driveの変更を
  自動で取り込むようになった。PDFなどアップロードしたファイルは対象外。
- 規程の正本は Box にあり、改定のたびに**別ファイル(別ID・日付入りのファイル名)**として置かれる。
  Box のバージョン機能は使われていない(versionNumber が1のまま)。

## 解法と、その理由
- GAS(無料)で、Box の規程フォルダ直下にあるファイルの本文を、**1つの固定のGoogleドキュメント**にまとめて書き出す。
  NotebookLM にはこのドキュメントだけをソースとして登録する。
- ファイルごとにドキュメントを作る案は採らなかった。改定のたびに新しいドキュメントができ、NotebookLM へ
  ソースを追加し直す手作業が残るため。自動同期が効くのは「既に登録したソースの中身の変更」だけで、
  新しいファイルの追加は自動ではない。
- 本文は Box が生成するテキストを使う。文字データの無いスキャンPDFは、Googleドライブの文字認識で読む。
  ただしPDFを丸ごと変換すると、外部の解説で2MB・10ページの制限があるとされ、19ページ・5.2MBのスキャンPDFは
  収まらない見込み。そこで Box のページ画像を1ページずつ変換し、ページ単位で結果を保存して実行時間の上限をまたいで再開する。

## うまくいかなかったこと
- 先に Claude API の Web アプリを作ったが、費用条件(追加課金なし)を最初に確認していなかったため作り直しになった。
  利用者向けの仕組みを提案するときは、ランニングコストを許容できるかを最初の選択肢の比較に含める。

## 抽出したルール / ヒューリスティック
- 「自動同期」を頼る設計では、同期の単位(ファイルID)と、正本の更新のされ方(上書きか、別ファイルの追加か)が
  一致しているかを確認する。一致しないなら、IDが変わらない中継ファイルを1つ挟む。
- 新しい仕組みを提案する前に、従量課金が発生してよいかを確認する(既存の契約内で済む案があるか先に探す)。
