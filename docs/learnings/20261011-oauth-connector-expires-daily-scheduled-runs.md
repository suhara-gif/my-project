# ユーザーOAuthのコネクタは約1日で切れる前提で、定期実行の書き込み経路を設計する

- 日付: 2026-10-11
- 種別: 調査
- 触れたファイル: upty-meta-ads.meta_ads.raw_ad_daily(BigQuery、10/09〜10/10 を補完)、meta-ads-autopilot/ROUTINE_PROMPT.md(参照のみ)

## 問題
トヨワク Meta 広告デイリー監視(Cowork の定期実行)が、9/29 以降ほぼ毎日、手順2(BigQuery への書き込み)で「sign in again」により停止した。
再接続すると一時的に直るが、翌日また止まる。

## 文脈
手順1(Meta 取得)は成功しており、止まるのは BigQuery コネクタ(ユーザーのOAuth)だけ。母艦のサービスアカウントは同じ BigQuery に期限なしで接続できる(`check_bq_auth.py` が OK_LIVE)。

## 解法と、その理由
`raw_ad_daily` の `fetched_at`(書き込みに成功した時刻)を時系列で並べて、成功した日の分布を見た(JST):

| 書き込み成功 | 補足 |
|---|---|
| 9/29 08:52、10:52 | 再接続の直後 |
| 10/07 08:53 | 9/30〜10/06 は毎日停止の後 |
| 10/09 18:52、10/10 08:52 | 10/09 の再接続の後。約14時間後の翌朝まで成功 |
| 10/11 08:53 | 失敗(約38時間後) |

再接続の後、約1日以内は書き込めるが、それを過ぎると必ず切れる。この形は、ユーザーOAuthに再認証の期限があるときの典型で、
Google Workspace の「Google Cloud セッション制御」(既定 16時間の再認証)に合う。**ただし管理コンソールの設定は未確認 [要確認]**。
サービスアカウントは再認証の対象外なので、期限の影響を受けない。

今回の対処は、承認範囲(10/09〜10/10 の補完と当日分のレポート)に限った。構造的な対処は、IAM とルーティン指示文の変更が要るため、再承認の対象にした。

## うまくいかなかったこと
- 母艦のサービスアカウントで `raw_ad_daily` を読む確認は 403(`upty-meta-ads` に権限が無い)。付与だけでは、手順1(Meta 取得)が Cowork 側にあるため、取得した行を母艦へ渡す経路が別に要る。

## 抽出したルール / ヒューリスティック
定期実行の書き込み先が、ユーザーOAuthのコネクタだけのとき、成功時刻の分布(再接続からの経過時間)を見る。約1日で切れているなら、
コネクタの再接続を運用で回さず、期限のない経路(サービスアカウント)に書き込みを移す案を、最初の選択肢として出す。
