# 「監視すべきか」のゲートはあっても「どの間隔で監視すべきか」のゲートが無かった

- 日付: 2026-08-24
- 種別: 設計判断
- 触れたファイル: CLAUDE.md(自動化ループのルール追記)

## 問題

PR #40・PR #42(いずれもドラフト、レビュアー無し)を1時間おきの `send_later` ループで
チェックインし続けた。人間が実際にPRへ反応する(draftを外す・マージする)までに要した
時間は、実測でPR #40が21時間24分、PR #42が21時間16分。この間、チェックは合計40回以上
繰り返され、そのほぼ全てが「変化なし」だった。

`docs/learnings/20260823-recurring-loop-needs-purpose-gate.md` は「そもそも監視対象
(CI・レビュアー)が存在するか」のゲートを追加したが、これはPR #40・#42には当てはまらない
——両PRともCIは存在した(shellcheck)。つまり「監視する理由はある」PRであっても、
「1時間おき」という間隔が人間の実際の応答速度(20時間超)に対して不釣り合いに短い
ケースが起きうることを見落としていた。

## 文脈

なぜ非自明だったか: 「約1時間後にチェックインする」は、PR監視の既定動作としてハーネス側
から明示的に指示される値であり、自分で選んだ設計ではない。既定値をそのまま使い続けることは
「指示に従っている」という点で一見正しく見えるため、それ自体を疑う発想が起きにくかった。

5 Whysで掘ると:
1. なぜ21時間超も1時間おきに鳴らし続けたか → チェックのたびに「変化なし」を確認し、
   ただ次の1時間後を再武装する、という既定の手続きをそのまま繰り返したから。
2. なぜ間隔を伸ばす判断をしなかったか → 「監視すべきか」の判定(CI有無)はCLAUDE.mdに
   ルール化されていたが、「監視する場合の間隔をどう調整するか」のルールが無かったから。
3. なぜそのルールが無かったか → 前回(20260823)の学びは「無駄な監視を無くす」ことに
   焦点を当てており、「必要な監視の頻度を最適化する」という別軸を扱っていなかったから。
4. なぜ別軸だと気付かなかったか → どちらも「ループの無駄をなくす」という同じ動機から
   生まれる問題に見えるが、前者は0/1判定(やるかやらないか)、後者は連続値の調整
   (どのくらいの頻度でやるか)であり、必要な仕組みが異なる。
5. (根本)なぜ自分で間隔を調整する発想が働かなかったか → ハーネスが与える既定値
   (「約1時間後」)を、状況に応じて上書きしてよい「初期値」としてではなく、
   そのまま守るべき「固定仕様」として扱っていたから。

## 解法と、その理由

- 「約1時間後にチェックイン」という既定値は、監視を始めた直後の初期値としては妥当
  (人間がすぐ反応する可能性を早期に拾える)。しかし、複数回「変化なし」が続いた場合は、
  それ自体が「この間隔は今のPRの反応速度に対して短すぎる」というシグナルなので、
  間隔を伸ばしてよい。
- 具体的な数値までは固定しない(PRの性質によって適切な値が変わるため)が、
  「N回連続で変化なしなら、次回以降の間隔を延ばすことを検討する」という判断ポイントを
  CLAUDE.mdに明記した。厳密なアルゴリズム(倍率など)は次に同じ状況が起きたときに
  実測しながら決める。

## うまくいかなかったこと

- 当初は「間隔を最初から可変にする」ことを考えたが、それは「初回から様子見の姿勢を取る」
  ことになり、20260823の学び(既定ルールは基本的に「見逃し」を防ぐために書かれている)と
  緊張関係にある。初回〜数回は既定の短い間隔を守り、それでも変化が無いと分かってから
  間隔を伸ばす、という段階的な設計の方が、20260823の教訓と矛盾しない。

## 抽出したルール / ヒューリスティック

**「監視すべきか」(0/1)と「どの頻度で監視すべきか」(連続値)は別のゲートである。**
前者だけをルール化しても、後者の非効率は防げない。既定値(ハーネスや過去の自分が決めた値)
は「今の状況でも最適」とは限らない初期値として扱い、実測(変化なしが何回続いたか)に
応じて調整してよい。
