# Notionの「第二の脳」は要約ではなくリンクで詰まる — raw/compiled を分けてパイロットを先に回す

- 日付: 2026-09-25
- 種別: 設計判断
- 触れたファイル: (Notion 上のみ) 🧠 情報の一元管理ページ / 🧩 トピック（知識ノート）/ 第二の脳 運用設計＆エージェント指示書

## 問題
Notionを「AIが勝手に整理・リンクする第二の脳」にしたい、なるべく手戻りなく、という依頼。
現状の入口DB(情報の一元管理ページ)は379件あり、AI要約(Notion AI autofill)は378件に付いていたが、
プロジェクトへのリンクは50件、「済」は47件だけだった。

## 文脈
- 「保存して終わり」の原因を「整理されていない」と捉えると、DB統合・タグ再設計・全件移行という
  大工事に向かいやすい。そうなると設計を途中で直すたびに379件ぶんの手戻りが出る。
- ワークスペースには取り込み用のDBが8つ以上あり(マイリンク、Felo.ai、Slack情報管理DBなど)、
  ハブページも2つある。散らかっていることが目に付きやすい。
- 入口DBには、レシート・髪型・ストレスチェックと、自分の設計書・外部記事が同じ列に混ざっていた。
- Notion Custom Agent がすでに運用されていた(ページ作成トリガー・定時トリガーの実績あり)ため、
  ローカルスクリプトではなくNotion内で自動化エンジンを完結させられる。

## 解法と、その理由
1. **数字で詰まりを特定した。** 要約の付与率が 99.7%、リンクの付与率が 13% だった。欠けているのは
   「つなぐ層」であって、「まとめる層」ではないと判断した。
2. **既存を動かさず、層を1つ足した。** 素材(raw)の入口DBはそのまま残し、コンパイル層として
   「🧩トピック」DB(1ページ=1つの考え方)を新設した。素材↔トピックは双方向リレーションにし、
   トピックからプロジェクト・人物へは既存DBへのリレーションを張った。実体DBは新しく作らない。
3. **入口DBには判定用のプロパティだけを足した。** 追加したのは「種別」(知識/作業ログ/記録/保留)と
   「AI処理日」の2つ。AI処理日が空の行だけを処理するので冪等になり、取りこぼしも毎日の定時実行で回収できる。
   記録(レシート等)はコンパイル対象から外し、ノイズがトピックに混ざらないようにした。
4. **一括自動化の前に、直近26件を手でコンパイルした(パイロット)。** その結果、トピック6件、
   知識7/7件・作業ログ7/10件がリンクされた。途中で「本文が空でURLだけの素材」が見つかり、
   「保留(推測で書かない)」ルールを指示書に追加した。一括実行の前に仕様の穴が1つ埋まった。
5. **エージェントのトリガーは「ページ追加」だけにした。** 「更新」をトリガーにすると、
   自分がプロパティを書き込んだことで自分が再起動するループになるため。
6. **統合・削除はAIに任せない。** 庭師エージェントは状態を「要統合」にして提案するだけにし、
   統合するかどうかは人間が判断する。

## うまくいかなかったこと
- Notion MCP の `update_data_source` で、自己リレーションを `RELATION(自DB, DUAL '逆名' 'id')` の形で
  2本同時に ADD した。その結果、「関連トピック 1」「関連トピック（逆） 1」という重複プロパティが
  自動生成され、4本になった。作ったばかりの空DBだったので4本とも DROP し、
  単方向リレーション1本に作り直した(双方向はエージェントが張り返す運用にした)。
- リレーション値に存在しないページIDを渡してもエラーにならず、そのまま受理されることがあった。
  IDを取り違えたときは、作成後の読み返しで気付く必要がある。

## 抽出したルール / ヒューリスティック
- 「整理されていない」という相談では、まず**要約率・リンク率・処理済み率を数えてから**設計する。
  最も低い率の層だけを足し、既存の素材を移動・改名・統合しない。
- AIに自動処理させるDBには必ず「処理済み日付」プロパティを置き、**空の行だけを処理する**ようにする。
  トリガーには「作成」を使い、「更新」は使わない。
- 全件自動化の前に、**直近20〜30件を手でコンパイルして仕様の穴を出してから**指示書を確定する。
- Notion MCP で自己リレーションを作るときは DUAL を使わず、単方向で作る。
  作成後はスキーマを読み返して重複プロパティが無いことを確認する。
