# リモート実行セッション(dispatch)はmacOSのlaunchd/ローカルファイルに触れない — 判定してから指示文にハンドオフする

- 日付: 2026-09-02
- 種別: 調査 / 設計判断
- 触れたファイル: なし(コード変更なし。母艦PCローカル実行への引き渡し指示文を作成)

## 問題

須原さんから「com.upty.git-backup / com.upty.yahoo-ads-sync の launchd 状態確認」「job_ledger_sync.py の
LAUNCHD_PREFIXES 実値確認」という調査依頼を受けた。このセッションは my-project リポジトリの
クローンしか持たないクラウド上のLinuxコンテナ(リモート実行環境)で動いており、`launchctl` コマンド自体が
存在せず、`~/Library/LaunchAgents` も存在しなかった。依頼された調査は原理的に実行不可能だった。

## 文脈

このリポジトリ(と須原さんのNotionナレッジベース)では、Claude Codeの実行環境が複数種類ある:
「母艦PC(自宅常時起動Mac)のローカルTerminal」「会社PC」「リモートのクラウドVM(=須原さんは
これを『ディスパッチ』と呼ぶ)」。launchd・plist・ローカルログファイルなど、macOS固有かつ
特定マシンのファイルシステムに紐づく状態は、そのマシンのローカル実行でしかアクセスできない。
この区別自体は須原さんのNotion側に既に「ディスパッチのVMは母艦とは別環境。……ディスパッチからは
実行不可」という形で明文化された運用ルールとして存在していた(複数ページで独立に確認済み)。

非自明だったのは、**このセッション単体では「自分がdispatchかどうか」「対象の状態がローカル固有かどうか」を
判定する材料が最初は無かった**点。CLAUDE.mdは各プロジェクトのCLAUDE.md/READMEを読めと指示するが、
「実行環境の種別を跨ぐ作業を代行できるか」の判定ルールはコード側のどこにも書かれておらず、
Notion側の運用ナレッジ(過去の別プロジェクトでの類似トラブル)を横断検索して初めて見つかった。

## 解法と、その理由

1. まず自セッションの実行環境を実際に確認した(`uname -a`、`which launchctl`、
   `ls ~/Library/LaunchAgents`)。推測せず、コマンドを打って「存在しない」ことを直接確認した。
2. リポジトリ内を検索したが `job_ledger_sync.py` や `LAUNCHD_PREFIXES` は見つからなかった
   (対象がこのリポジトリの管理外にあると判明)。
3. ユーザーから「母艦PC?会社PC?」と聞かれた際、このセッションからは分からないと正直に答えた
   うえで、Notionの運用ナレッジ(`ツール・自動化ジョブ台帳`、`自動化ジョブ台帳｜自動更新の設計`)を
   検索し、「実行場所: 母艦PC」という直接確認済みの記載を発見した。これで初めて対象マシンを特定できた。
4. 「dispatchで遂行できそうか」を問われた際は、Notion内の別プロジェクトのページ
   (`Salesforceレポート→Googleスプレッドシート同期スクリプトの作成`)に明記されていた
   「ディスパッチのVMは母艦とは別環境……ディスパッチからは実行不可」という**既存の確立済みルール**を
   根拠に「不可」と判定した。自分の推測ではなく、須原さんの過去の運用ナレッジを一次情報として使った。
5. 実行不可と判定した対象については、当初の調査依頼の文言をほぼそのまま維持しつつ、
   母艦PCのローカルTerminal(ローカルClaude Code)にコピペできる自己完結した指示文を作成して
   ハンドオフした。指示文には前回Notion記録の参考情報も添え、「要再検証」と明記した
   (未確認の推測をそのまま確定情報として渡さないため)。

他の候補として「とりあえず`launchctl`を実行してエラーを見せる」という手もあったが、
存在しないコマンドを試して失敗を報告するより、環境確認を先に済ませてから
「原理的に不可能」と明言するほうが、須原さんの手戻りが少ないと判断した。

## うまくいかなかったこと

なし。ただし最初のユーザーへの回答時点では「不明」「実機で確認してください」とだけ答えており、
「どの実機か」まで特定できていなかった。Notion検索を提案されて初めて、自分から確認できる
情報源(Notion)が手元にあったことに気づいた——最初の応答の時点でNotion検索を自発的に
試すべきだった、という反省点は残る。

## 抽出したルール / ヒューリスティック

- **依頼された調査・操作の対象が「特定のローカルマシンの状態」(launchd、ローカルファイル、
  ローカルプロセス等)かどうかを、着手前に必ず切り分ける。** 切り分け方は「自セッションの
  実行環境で対象コマンド/パスが実在するか」を実際に叩いて確認する(推測しない)。
- **「このリモートセッションで完結できるか」の判定材料は、コードだけでなくNotion等の
  運用ナレッジベースにも既に確立されている場合がある。** 実行不可能に見える依頼を受けたら、
  即座に「できません」で終わらせず、過去の類似トラブル(別プロジェクトの運用ルールでも)を
  横断検索してから結論を出す。
- **実行不可と判定した作業は、依頼内容をそのまま複製した自己完結の指示文に変換して
  ローカル実行環境へハンドオフする。** その際、参考情報として過去の記録を添えるなら
  「要再検証」と明記し、確定情報として押し付けない(CLAUDE.mdの前提チェックルールと同じ理由)。
