# Box本文取得が空=「文書が空」ではない。スキャン画像PDFを見分けてから報告する

- 日付: 2026-10-08
- 種別: 調査 / 設計判断
- 触れたファイル: kitei-qa/src/Box.gs, kitei-qa/src/Code.gs, kitei-qa/README.md

## 問題
就業規則Q&Aの仕組みを検討する際、Box MCP の `get_file_content` で就業規則PDFの本文を取ろうとしたら
出力が空だった。これをユーザーに「本文が空でした」と報告したところ、「空じゃないと思うよ」と返された。

## 文脈
ユーザーにとってPDFは「開けば読める文書」なので、「空」は「中身が無い」と受け取られる。
実際には、ファイルは5.2MBあり、見た目には19ページの本文がある。空だったのは**文字データ(テキスト層)**だけ。
`pdfinfo` の Creator が `RICOH IM C3510 JPN`(複合機)、`pdffonts` がフォント0件、`pdftotext` が0文字で、
紙をスキャンした画像PDFだと確定できた。同じフォルダの給与規程PDFは文字データがあり、正常に取れた。

## 解法と、その理由
1. 報告では「中身が空」ではなく「見た目には本文があるが、文字データが入っていない(スキャン画像)」と
   区別して書く。対策も変わる(ファイルを探す → 元データから書き出したPDFに差し替える)。
2. アプリ側は、読めないファイルを黙って捨てずに `unreadable` として画面に警告し、モデルにも
   「このファイルは内容不明」と渡す。読めない規程があることに気づかず「記載なし」と誤答するのを防ぐため。
3. 自動OCRの組み込みは見送った。労務規程は日数・金額の読み間違いがそのまま誤回答になるため、
   元データから書き出したPDFを正本にする運用の方が安全と判断した。

## うまくいかなかったこと
- ファイルサイズ(5.2MB)と取得文字数(0)の食い違いを見た時点でスキャンを疑うべきだったが、
  ユーザーに指摘されるまで「空」という言葉で報告していた。

## 抽出したルール / ヒューリスティック
- PDFからの本文取得が空/極端に短いときは、「空」と報告する前に `pdffonts`(フォント0件ならスキャン)と
  `pdfinfo` の Creator(複合機名ならスキャン)を確認し、「文字データが無い」と書く。
- 文書を読み込む仕組みでは、読めなかったファイルを利用者に見える形で警告する。黙って除外しない。
