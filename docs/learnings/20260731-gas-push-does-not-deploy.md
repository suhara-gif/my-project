# `clasp push` は本番を更新しない — 「直したのに直らない」の正体と、その検出手段

- 日付: 2026-07-31
- 種別: バグ修正 / 運用設計
- 触れたファイル: `slack-inbox-to-notion/tools/release.mjs`,
  `slack-inbox-to-notion/tools/verify-deployed.mjs`,
  `slack-inbox-to-notion/slack_inbox_to_notion.gs:19`(SCRIPT_VERSION), `doGet`

## 問題

Slack の 📥 を全チャンネルで拾えるようにコードを直し、`clasp push` した。
ローカルもエディタ上のコードも直っている。なのに Slack から押しても挙動が変わらない。

真因は **Web App のデプロイがバージョン1に固定されたまま**だったこと。
`clasp push` が更新するのはエディタで見える HEAD だけで、
**Slack が叩く URL は、デプロイした時点のバージョンを配信し続ける**。

さらに悪いことに、この案件では GAS プロジェクトが「デフォルトの GCP プロジェクト」のため
**`doPost` の実行ログが展開できない**。`skip:` の理由も例外も読めないので、
「押しても何も起きない」以上の情報が取れず、切り分けが実測(Notion の件数増減)頼みになった。

## 文脈

なぜ非自明か。

- **push と deploy が別概念であることは知っていた。**実際このリポジトリの README には
  「GAS はコードを保存しただけでは公開版に反映されません」と自分で書いてあった。
  それでも実作業では「プロパティ変更だけだから再デプロイ不要」と繰り返し指示していた。
  **直前の変更がコード変更だったのに、設定変更のつもりで喋っていた。**
  知識の欠落ではなく、**変更の種類を取り違えたまま手順を出した**ことが原因。
- エディタから関数を実行すると **HEAD が動く**。だから `testConfig` も `testRegister` も
  正常に通る。**「テストは通るのに本番だけ古い」**という、最も紛らわしい状態になる。
  実際、デプロイが v1 のまま(全チャンネル skip)の時間帯に、
  `testRegister` 由来の Notion ページが1件でき、状況をさらに混乱させた
  (`runFromTestUrl_` は `handleEventCallback_` を通らず `registerReaction_` を直接呼ぶため、
  チャンネル判定を通らない)。

## 解法と、その理由

**「気をつける」で終わらせず、2つの仕組みにした。**

1. **`npm run release`** — push と「既存デプロイの更新」を1コマンドに束ねた。
   `clasp deploy -i <既存のデプロイID>` を使うので **URL が変わらない**
   (`clasp deploy` を素で叩くと新規デプロイになり URL が変わって Slack の再設定が要る)。
   最後に配信中コードを検証するところまで含める。
   → **push だけして deploy を忘れる**という失敗経路自体を消した。

2. **`doGet` が `SCRIPT_VERSION` を返す + `npm run verify:deployed`** —
   GAS は自分のソースを読めないので、コードに埋めた定数を配信版に自己申告させ、
   ローカルの値と突き合わせる。**「いま本番で動いているのはどのコードか」を外から観測できる**
   ようにした。ログが読めない環境でも、ズレだけは1コマンドで判定できる。

なぜ「ログを読めるようにする」を先にやらなかったか: それは GCP 標準プロジェクトへの
切り替えが必要で、本人の作業が増えるうえ、**ログが読めてもデプロイのズレは
「何も起きない」としか見えない**(イベントが古いコードで skip されるだけ)。
順序として、観測点を作るほうが安い。ログ可視化は README に運用改善として残した。

## うまくいかなかったこと

- **「再デプロイは不要です」と繰り返し断言した。**プロパティ変更については正しいが、
  直前にコード変更を入れていたので誤り。相手に半日分の切り分けをさせた。
- 検証を Notion の「ステータス別」ビューの INBOX 件数だけで見ていた時期があり、
  成功を一度「失敗」と誤判定した(別の自動化が後からステータスを書き換えていた)。
  **観測手段が対象の唯一の真実でないなら、実体を直接見る。**

## 抽出したルール / ヒューリスティック

- **GAS で「コードを変えたら」`npm run release`。`push` だけで終わらせない。**
  変更が「コード」か「設定」かを毎回口に出して分ける。
  設定(スクリプト プロパティ)のみ → デプロイ不要。コード(`.gs`)→ デプロイ必須。
- **「直したのに直らない」と言われたら、まず配信中のバージョンを疑う。**
  ローカル・エディタ・**デプロイ**は別物。エディタ実行が通ることは本番の証拠にならない。
- **本番の同一性は、外から観測できる形にする。**
  デプロイ物にバージョンを自己申告させ、突き合わせるコマンドを1つ用意する。
  「気をつける」は再発防止ではない。
- **ログが読めない環境では、観測点を作るコストを先に払う。**
  そうしないと毎回ゼロから切り分けをやり直すことになる。
- 手順を人に出す前に、**直前の自分の変更がどの種類だったかを確認する。**
  一般論として正しい説明でも、直前の変更に対して誤っていれば有害。
