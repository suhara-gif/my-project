# 手順を案内する前に、既存の「書き込み経路」の痕跡を探す

- 日付: 2026-09-29
- 種別: 失敗した試み / 調査
- 触れたファイル: google-ads-mcp の `0_`〜`4_` 死活監視追加 .command、`5_死活監視にUNKNOWN集約を追加.command`

## 問題
Mac 側の死活監視スキル(`~/Documents/Claude/Scheduled/.../SKILL.md`)への追記を、「エディタで開いて貼って保存してください」と案内した。
結果、「ファイルがロックされています」「フォルダに保存するためのアクセス権がありません」の2種類のエラーで、3往復を費やした。
さらに、返信「1」を確認コマンドの結果だと決めつけて「保存済み」と報告し、見張りのメモにも書き込んだ(実際は未保存)。

## 文脈
リポジトリには、同じスキルに Step を追加するための `.command` が既に4本あった(`0_`〜`4_`)。
そのヘッダには「`~/Documents/Claude/Scheduled/` 配下は Claude のセッションから書き込み禁止のため、母艦側で差し替える」と、経路の理由が書いてあった。
別の案内をする前に `ls *死活監視*.command` を1回実行していれば、最初から分かっていた。

## 解法と、その理由
- 既存の `.command` と同じ方式(母艦側で python が既存ファイルの中身を書き換える)で `5_` を作った。
- 新規ファイルを作る操作(エディタの保存・同じフォルダへのバックアップ)は、フォルダの書き込み権限を要する。既存ファイルの上書きは要らない。この違いが、今回の失敗の分かれ目だった。
- バックアップはデスクトップに作り、二重挿入しない・挿入位置が無ければ中止する仕組みにした。擬似ファイルで5パターンを確認した。

## うまくいかなかったこと
- 「ロックされています」を `chflags nouchg` で直そうとした。実際にはフォルダ側の権限も原因で、エディタの保存方式そのものが合っていなかった。
- 「1」という短い返信の意味を確かめず、都合のよい解釈で先に進んだ。

## 抽出したルール / ヒューリスティック
1. 人に手作業を案内する前に、同じ対象への過去の変更手段(`.command`、過去のPR、学びノート)を `ls` / `grep` で探す。あれば、それに倣う。
2. 保護されたパスを書き換える案内では、「エディタで保存」を最初の案にしない。既存ファイルの中身を書き換えるスクリプトを使う。
3. 短い返信(「1」など)が結果の報告なのか選択なのか曖昧なときは、状態を確かめる1コマンドを返す。確認できるまで「済み」と記録しない。
