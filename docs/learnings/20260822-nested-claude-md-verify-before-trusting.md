# 「ネストされたCLAUDE.mdは自動で読まれる」を裏取りせずに人に説明してしまった

- 日付: 2026-08-22
- 種別: 調査 / 失敗した試み
- 触れたファイル: CLAUDE.md, claude-backup/CLAUDE.md, second-brain/vault-template/CLAUDE.md

## 問題

ルートの `CLAUDE.md` が claude-backup 専用ルールになっていたため、リポジトリ全体向けに
汎用化し、claude-backup 固有の詳細ルールを `claude-backup/CLAUDE.md` へ分離した。その際、
「`second-brain/vault-template/CLAUDE.md` と同じディレクトリスコープのパターンです」と
ユーザーに説明し、PR本文にも同じ根拠を書いた。

## 文脈

第三者レビュー観点で自分の説明を検証したところ、2つの問題が見つかった。

1. **根拠にした実例が誤り。** `second-brain/vault-template/CLAUDE.md` は、`new-vault.sh` が
   このリポジトリの外側(例: `~/vault`)に**別の新しいgitリポジトリ**として複製するテンプレート
   であり、`my-project` リポジトリ内でサブディレクトリとして自動検出されているCLAUDE.mdでは
   ない。「既にこのリポジトリで動いているパターン」という説明は事実誤認だった。
2. **仕組み自体の発火が未検証だった。** Claude Code公式ドキュメント
   (https://code.claude.com/docs/en/memory)によれば、サブディレクトリのCLAUDE.mdは
   「Claudeがそのディレクトリ配下のファイルを読んだときに文脈へ追加される」仕組みで、
   セッション開始時の自動ロードとは別枠。実際にこのセッション(リモート実行環境)で
   `claude-backup/run-backup.sh` と `claude-backup/install.sh` をReadツールで読んでみたが、
   `claude-backup/CLAUDE.md` の内容が文脈に追加された形跡(system-reminder等)は無かった。
   加えて `anthropics/claude-code` issue #2571 でも同種の不具合報告がある。
   → 「動く前提」で説明していたが、少なくともこの環境では確認できず、機能しない可能性がある。

## 解法と、その理由

- claude-backup 固有ルールの分離自体(`claude-backup/CLAUDE.md` を新設)は妥当なので撤回しない。
  ただし「自動で読まれる」への依存を単一障害点にしない設計に修正した。
- ルートの `CLAUDE.md` に「サブディレクトリで作業するときはそのCLAUDE.md/READMEを**明示的に
  Readしてから**着手する」を明記し、自動検出が発火しない場合でもルールが失われないようにした。
  これはこのリポジトリ自身が持つ「どの失敗経路でもローカルアーカイブは必ず残す」という
  設計原則(退避なしの喪失を許さない)と同じ考え方を、バックアップデータではなく
  「運用ルールの喪失」に適用したもの。
- 不正確だった説明(vault-templateとの類比)はPR本文から削除し、実際に検証した内容に
  差し替えた。

## うまくいかなかったこと

- 最初、`second-brain/vault-template/CLAUDE.md` の存在だけを見て「同じパターンが既に
  このリポジトリで使われている」と類推した。実装(new-vault.shの複製先)を確認せずに
  類推で断定してしまったのが誤りの原因。

## 抽出したルール / ヒューリスティック

**「既存のファイルが存在する」ことを「その仕組みが今のコンテキストで実際に機能している
証拠」として扱わない。** 特に「Xと同じパターンです」という類比でユーザーに説明するときは、
類比先の実装(誰が・いつ・どこで生成/使用するか)まで読んでから言う。加えて、ドキュメントに
「〜という仕組みがある」と書かれていても、それが**今のセッション/環境で実際に発火するか**は
別問題として扱い、可能なら安価な実地テスト(該当ディレクトリのファイルをReadしてcontext変化を
見る等)で確認してから、その仕組みへの依存を設計の前提にする。確認できないなら、その仕組みが
効かなくても壊れないフォールバック(ここでは「明示的にRead」)を必ず用意する。
