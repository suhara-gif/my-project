# GAS の doPost は HTTP ヘッダを読めない — Slack Webhook を「速く返す」でなく「冪等」で守る

- 日付: 2026-07-30
- 種別: 設計判断
- 触れたファイル: `slack-inbox-to-notion/slack_inbox_to_notion.gs`, `slack-inbox-to-notion/README.md`

## 問題

Slack の `reaction_added` を Google Apps Script の Web App で受け、Notion にタスクを作る
仕組みを組んだ。Slack Webhook の教科書的な作法は次の 2 つだが、GAS ではどちらも**そのまま実装できない**。

1. `X-Slack-Signature` / `X-Slack-Request-Timestamp` で署名を検証する。
2. 3 秒以内に 200 を返し、重い処理は非同期に逃がす。

## 文脈

なぜ非自明か。

- GAS の `doPost(e)` に渡る `e` は `postData` / `parameter` / `parameters` / `queryString` /
  `contextPath` / `contentLength` だけで、**リクエストヘッダを含まない**。
  署名検証は「実装が面倒」ではなく**プラットフォーム上不可能**。ここを踏み外すと
  「あとで署名検証を足せばいい」という前提で設計を進めてしまう。
- GAS には真の非同期実行が無い。時間主導トリガは**最短1分間隔**なので、
  「即 200 → 後で処理」を選ぶとキュー用のストレージとトリガ管理が丸ごと増える。
- 一方で Slack は 3 秒で再送する。Slack API 3 本 + Notion API 3 本を直列に叩くと
  3 秒は普通に超える。**再送は「起きるかもしれない例外」ではなく「常時起きる前提」**。

## 解法と、その理由

**「速く返す」を諦め、「何回来ても結果が変わらない」に振った。** 具体的には三重の重複排除:

1. `LockService` のスクリプトロック — 再送が同時到着したときの競合を直列化する。
2. `CacheService` に `event_id` を 1 時間記憶 — Slack の再送(最長5分程度)を弾く。
3. Notion 側「Slackリンク」の完全一致検索 — キャッシュ失効後や後日の押し直しを弾く。

3 が最終的な正で、1・2 は 3 に到達する前の競合を潰す前段。**永続的な真実を外部システム
(Notion)側の一意キーに置く**と、GAS の揮発的な状態(キャッシュ・ロック)が消えても壊れない。

署名検証の代わりは **Request URL のクエリ共有シークレット**(`?key=…`)。ヘッダが読めなくても
`e.parameter` は読める。ただしこれは署名検証の等価物ではない(リプレイ防止にならない)ので、
**入口以外の門番**も残した — 押した人を `ALLOWED_SLACK_USER_ID` の1名に限定し、
重複排除で「本人が押した実在メッセージ1件」しか作れないようにしてある。

エラー時は **200 でなく 500 を返す**。握り潰すと「押したのに何も起きない」が無言で発生する。
重複排除が効いているので、Slack に再送させるほうが安全側。

もう1つ。**`url_verification` の challenge 応答を、他の設定検証より前に置いた**。
そうしないと「トークン未入力 → URL 登録すら Verified にならない」で、
セットアップ中の切り分けが「Slack 側が悪いのか GAS 側が悪いのか」で詰まる。
**セットアップの最初の一歩は、設定が半分でも通るようにする。**

## うまくいかなかったこと

- 「即 200 を返して時間主導トリガで後処理」案は退けた。GAS のトリガ最短が1分なので
  📥 を押してから Notion に出るまで最大1分ラグが出る上、キューの永続化と失敗時の
  再処理を自前で持つことになり、部品数が倍になる。重複排除だけで守れるなら不要。
- `conversations.info` でチャンネル名を取る案も退けた。`channels:read` スコープが1つ増える。
  チャンネルは1つに固定なので、任意プロパティ `TARGET_CHANNEL_NAME` で置き換えた。
  **スコープが増える機能は、設定値で代替できないか先に考える。**
- permalink をワークスペースドメインから自前で組み立てる案も退けた。重複判定キーが
  `chat.getPermalink` の返す形式とずれ、同じメッセージが2件登録される。
  **一意キーは必ず単一の発生源から取る。**

## 抽出したルール / ヒューリスティック

- **GAS の `doPost` でヘッダ由来の検証(HMAC 署名・独自ヘッダ)を設計に含めない。**
  `e` にヘッダは無い。認証が要るならクエリ文字列の共有シークレット + 業務ロジック側の門番で組む。
- **3 秒以内に応答できない Webhook 受け口は、「速くする」より先に「冪等にする」。**
  再送で二重作成が起きないと言えるまで、レイテンシ最適化に手を付けない。
- **冪等性の最終的な根拠は、外部システム側の一意キー(今回は Notion の URL プロパティ)に置く。**
  GAS のキャッシュ・ロックは補助であって根拠にしない。
- **セットアップの疎通確認(challenge 応答・疎通用エンドポイント)は、設定値の検証より前に返す。**
- 追加スコープ/権限が必要な機能は、固定値の設定項目で代替できないかを先に検討する
  (CLAUDE.md「判断がつかないときは権限を狭める側に倒す」の具体例)。
- **`.env.example` の placeholder は `<説明文>` の形で書く。**`xoxb-000000-…` のように
  本物の**形**を真似ると、GitHub の push protection がダミーでも秘密情報として
  push を拒否する(実際に今回ブロックされた)。**このとき unblock URL で例外承認しない** —
  placeholder の書き方を直すのが正しい対処で、例外承認は「秘密を通す穴」を恒久的に開ける。
