# 「変化検知」ループに「そもそも検知対象があるか」の起動ゲートを入れ忘れた

- 日付: 2026-08-23
- 種別: 設計判断 / 失敗した試み
- 触れたファイル: CLAUDE.md(自動化ループのルール追記)

## 問題

PR #44(CLAUDE.md汎用化)を作成した際、既定動作に従い `subscribe_pr_activity` で購読し、
さらに「約1時間後に自分をチェックインさせる `send_later` ループ」を組んだ。このPRは
CIが1件も設定されていないdocs変更のdraft PRで、レビュアーも付いていなかった。にもかかわらず
ループは「変化なければ黙って再武装する」仕様のまま3周した(いずれも「変化なし」)。
ユーザーから「意味がないと自分で判断できるものをなぜ放置するのか」と指摘されて気づいた。

## 文脈

なぜ非自明だったか: 「PRを作ったら監視する」「webhookは信頼できないので補助ポーリングを
組む」はどちらもシステム側の既定ルールとして正しい。問題は、この既定ルールを**個別PRの実態
(CI設定の有無)を見ずに機械的に適用し続けた**こと。1回目のチェックで既に「CIチェック0件・
レビュースレッド0件」と分かっていたのに、ループ側にはその判定結果を「補助ポーリングを止める」
というアクションに繋げる仕組みが無かった。

5 Whysで掘ると:
1. なぜ無価値な再武装が続いたか → 「変化なければ黙って再武装」の指示をそのまま繰り返し実行したから。
2. なぜ初回で気付いた「見るべきものが無い」を反映しなかったか → ループに終了条件が
   「変化があったか」しか無く、「そもそも検知対象があるか」を見る条件が無かったから。
3. なぜその条件を自分で足さなかったか → 「PR作成→購読→補助ポーリング設定」を一連の
   手続きとして機械的に実行し、個別PRの特性(CI無し)に応じて手続きを調整する発想が
   その場になかったから。
4. なぜ調整する発想が無かったか → 既定ルールは「もっと監視すべき」方向の失敗(見逃し)を
   防ぐために書かれており、「監視しすぎ」方向の失敗(無価値な反復)を防ぐ条件が
   既定ルール側に明示されていなかったから。
5. (根本)なぜそのギャップを自分の判断で埋めなかったか → 自己スケジュールした反復タスクを
   「指示への準拠」として実行しており、反復のたびに「これは今も目的に適っているか」を
   再評価する習慣が無かった。変化検知(state diff)と目的検証(purpose check)を
   別々のゲートとして持っていなかった。

## 解法と、その理由

- 補助ポーリング(`send_later`の再武装ループ)と、webhookイベント購読(`subscribe_pr_activity`)を
  分けて扱うことにした。購読は「人間が将来コメントする可能性」に備えて残す価値が常にあり、
  コストもほぼゼロ(イベント駆動)。一方、補助ポーリングは「webhookが取りこぼす可能性がある
  情報(CI成否・新規push・マージ衝突)」をカバーするためのものなので、**そのPRにCIが
  1件も設定されていない場合は、そもそもwebhookが取りこぼす情報自体が存在せず、補助
  ポーリングを組む理由が無い**。
- 「ルールだから」ではなく、初回チェックの結果(CI件数・レビュースレッド数)を見て、
  補助ポーリングの要否をその場で再判定するようCLAUDE.mdに明記した。

## うまくいかなかったこと

- 最初「CI/レビュアーが無ければ監視自体(購読含む)を全部やめる」という一般則にしようとしたが、
  第三者レビュー観点で見直すと、購読まで止めると将来ユーザー本人がPRにコメントした場合に
  気付けなくなるリスクがあった。購読とポーリングを同一視したのが誤り。

## 抽出したルール / ヒューリスティック

**自分で「変化があるまで繰り返す」ループを作るときは、"変化検知"のゲートとは別に
"そもそも検知対象が存在するか"のゲートを起動時に必ず入れる。** 既定ルールに書かれた手続きを
実行するときも、個別ケースの実測値(今回はCIチェック数=0)を見た時点で、手続き自体の要否を
その場で再評価する。「ルールに従っている」ことは「今この反復が価値を生んでいる」ことの
証明にならない。
