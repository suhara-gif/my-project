# 定期実行がOAuthコネクタ1本に依存すると、認証切れで毎朝止まる

- 日付: 2026-10-09
- 種別: 設計判断
- 触れたファイル: meta-ads-autopilot/ROUTINE_PROMPT.md, src/meta_autopilot/bqtool.py, src/meta_autopilot/ingest/bq.py, README.md

## 問題
朝の自律ルーティンが BigQuery コネクタ(OAuth)の未認証で止まった。`bq` CLI も `Invalid Credentials`
(実行環境の `CLOUDSDK_AUTH_ACCESS_TOKEN` は短命トークン)。人が再認証するまで復旧できない。

## 解法と、その理由
1. 取得より前に BigQuery の死活だけ確認し、ダメなら1行DMで止める(既存データを壊さず、原因が即わかる)。
2. 経路を二重化: サービスアカウント鍵(環境変数 `BQ_SERVICE_ACCOUNT_JSON`)を使う Python クライアント経路Aを優先し、
   コネクタを予備の経路Bにする。鍵は OAuth のように外れない。原因が OAuth の期限切れか別かを特定しなくても効く。
3. 付随して、巨大な結果(35日分JSON 15万文字)や18KBのINSERT文がモデルの文脈を通る問題が、ファイル入出力
   (`bqtool export-rows` / `load-rows`)で解消する。書き込み前の機械チェック(cv の NULL は Mechanic_Lead のみ許可)も入る。
4. `MAX(date)` 基準の窓は、取り込み未実行でも古いデータを正常に見せる。取り込み後に最新日が昨日か確認する。

## うまくいかなかったこと / 未確認
- 経路Aの実BigQueryへの実行は未確認(鍵が無いため。単体テストは鍵の検証と入力チェックのみ)。
- 環境変数が秘匿値扱いか、組織ポリシーで鍵の作成が禁止されていないかは未確認。
- 切断の原因(期限切れ/未接続)は未特定。

## 抽出したルール / ヒューリスティック
- 無人実行が人の再認証を要する手段1本に依存するなら、鍵なし/長寿命の予備経路を用意し、両方失敗で止まる設計にする。
- 「再認証した」はセッションに即反映されるとは限らない(この会話では再認証後もしばらくツールが見えなかった)。
- 原因が未特定でも効く対策(経路の二重化)と、原因特定を要する対策(トークン期限の調査)を分けて提示する。
