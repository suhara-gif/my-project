# 2つの外部サービスの設定が相互依存するとき、片方の定義ファイルを2段に割る

- 日付: 2026-07-31
- 種別: 設計判断
- 触れたファイル: `slack-inbox-to-notion/slack-app-manifest.yml`,
  `slack-inbox-to-notion/slack-app-manifest.with-events.yml`,
  `slack-inbox-to-notion/tools/gen-setup-properties.mjs`

## 問題

Slack App と GAS Web App を繋ぐセットアップを「人間の手作業を最小に」まとめようとしたら、
手順が一列に並ばなかった。

- GAS の設定検証(`testConfig`)には **Slack の Bot Token** が要る → Slack App を先に作る必要がある
- Slack の Event Subscriptions には **GAS の Web App URL** が要る → GAS のデプロイが先に要る
- しかも Slack はマニフェスト適用の瞬間に `request_url` へ challenge を投げる
  → URL が生きていないとマニフェストの保存自体が弾かれる

「Slack App マニフェスト1枚を貼れば完成」という当初の形は、この循環のため**原理的に成立しない**。

## 文脈

なぜ非自明か。マニフェストは「アプリの完成形を1枚で宣言するもの」に見えるので、
全部入りの1ファイルを作りたくなる。実際それは書けてしまうし、レビューでも通る。
**壊れるのは人間が実際に上から順に実行したときだけ**で、書いている側からは見えない。

同種の罠は他にもある。GAS 側では「スクリプト プロパティを CLI で設定する API が存在しない」。
`clasp` のコマンド一覧を眺めても「無いこと」は目に入らないので、
自動化計画に穴が開いたまま手順書が完成してしまう。

## 解法と、その理由

**マニフェストを「①アプリ作成用(URL なし)」と「②Request URL 登録用(URL あり)」の
2ファイルに割った。** それぞれの冒頭に「なぜ2つに分かれているか」を書いた。

これで手順が一列に並ぶ:
①でアプリ作成 → Bot Token 取得 → GAS 設定・検証 → デプロイ → URL 取得 → ②で URL 登録。

①は**書き換え不要でそのまま貼れる**、②は**1行だけ書き換える**、と
人間の作業量を段ごとに最小化した。分割の代償(ファイルが2つになる)より、
「順番どおりにやれば必ず通る」ほうが価値が高い。

スクリプト プロパティのほうは、**`.env.local` → 使い捨ての `.gs` を生成 → push →
エディタで1回実行 → 削除**という経路にした。API が無いので「完全自動」は諦め、
**人間の操作を『値を9個打ち込む』から『関数を1回実行する』に縮める**方向で解いた。
生成物は `.gitignore` に入れ、後始末コマンド(`npm run props:clean`)を先に用意した
(消し忘れると秘密の実値が GAS プロジェクトに残るため、後始末は手順ではなくコマンドにする)。

## うまくいかなかったこと

- 全部入りマニフェスト1枚案。書けるが、貼った瞬間に Slack が URL 検証で弾く。
  **「設定ファイルとして正しい」と「その順序で実行できる」は別物。**
- `clasp run` でスクリプト プロパティを設定する案。技術的には可能だが、
  GCP プロジェクトの差し替えと OAuth クライアント作成が必要で、
  **自動化のセットアップ手順のほうが、自動化したい手作業より長くなる**ので退けた。

## 抽出したルール / ヒューリスティック

- **セットアップ手順を書いたら、依存の向きを矢印で書き出して循環がないか確かめる。**
  循環があるなら、片方の定義ファイル/手順を「循環を切る位置」で2段に割る。
- **「設定ファイルとして妥当か」ではなく「上から順に実行して通るか」で検証する。**
  宣言的な設定ファイル(マニフェスト・IaC)ほどこの罠にはまる。
- **自動化の是非は「実装できるか」でなく「自動化の準備工数 < 削減できる手作業」で決める。**
- **秘密の実値を含む中間生成物を作るときは、生成コマンドと同時に後始末コマンドを用意し、
  先に `.gitignore` へ入れる。**後始末を手順書の文章にしない。
- 手順書には「できないこと」(初回 OAuth 認可・API 有効化トグル等)を表で明示する。
  できない理由を書かないと、読む側は自分の操作ミスを疑って時間を溶かす。
