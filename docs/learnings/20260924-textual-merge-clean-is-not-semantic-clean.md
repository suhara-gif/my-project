# 「git が衝突を出さない」は「マージ結果が正しい」を意味しない — 設定JSONの重複キーで保護が黙って消える

- 日付: 2026-09-24
- 種別: 調査 / 設計判断
- 触れたファイル: `.claude/settings.json`(PR #45 / #49)、`CLAUDE.md`(PR #57 / #58)

## 問題
未マージのPR 21件を仕分ける際、初版は「#45 と #49 は重複(どちらも permissions.deny)」と判断していた。
実際に main へ順番に仮マージすると、2本とも**衝突なしで通った**。ところが結果の
`.claude/settings.json` には `permissions` キーが2つあった。#45 はファイル先頭、#49 は末尾に追加していたためである。
Python の `json.load` は後勝ちなので、#45 の deny(`.env` の読み取り禁止、bypass モードの無効化など)は
**エラーも警告も出さずに消えていた**。2本は重複ではなく、禁止対象の異なる補完関係だった。

## 文脈
- git の衝突検出は「同じ行の近くを両側が変えたか」しか見ない。JSON のキーの一意性は見ていない。
- JSON 仕様上、キー名は一意であるべき(SHOULD)とされるだけで、重複時の挙動は処理系しだい。
  多くのパーサは後勝ちで、エラーにならない。
- 権限設定は「効いていない」ことが平常時には見えない。壊れても誰も気づかない種類の設定である。

## 解法と、その理由
- PR 同士を main へ**実際に順番に仮マージ**した(`git worktree` 上で `git merge`)。
  あわせて結果のファイルを `object_pairs_hook` でパースし、重複キーを検出した。
  git の終了コードだけでは不十分と判断したため。
- 修正方針は、2本の deny を1つの `permissions` にまとめること。
- ただしこの統合の push は、自動モードの安全判定(Self-Modification)で拒否された。
  Claude が自分の権限設定を書き換える操作にあたるため。回避はせず、人間の作業として残した。

## うまくいかなかったこと
- 初版は PR のタイトルと変更ファイル名だけで「重複」と判定していた。差分の中身を見ていなかった。
- `.claude/settings.json` の permissions を Claude 側で変更・push しようとして拒否された。
  権限設定の変更は、最初から人間に渡す段取りにすべきだった。

## 抽出したルール / ヒューリスティック
1. **構造化された設定ファイル(JSON/YAML/TOML)を触るPRが2本以上あるときは、git の衝突有無ではなく、
   順番に仮マージした結果のファイルをパースして検証する(JSON なら重複キーの検出)。**
2. 「重複PR」と判定する前に、差分の中身(追加される値)を突き合わせる。タイトルやファイル名の一致は根拠にしない。
3. `.claude/settings.json` の `permissions` の変更は、自動モードでは Claude 自身が実行できない前提で、
   最初から人間の作業として切り出す。
