# 観察を推奨アクションへ昇格させる前に、依存している前提を列挙して確認済みかを付す

- 日付: 2026-08-17
- 種別: 失敗した試み / 調査
- 触れたファイル: CLAUDE.md:115-124（「観察を昇格させるときの前提チェック」を追加）
  ／ 分析の成果物自体は Artifact として公開、リポジトリ外

## 問題

Claude の週間クレジット消費を分析し、改善プランを提示した。その第3位に
「**未使用の Fable 週間枠を活用する（実質的な増枠）**」を置いた。根拠は依頼者の使用状況画面の実測で、
週間制限に「すべてのモデル 2%」「Fable 0%」と2本のバーが並んでいたこと。
Fable が別枠なら、そこへ作業を寄せれば本体の枠を使わずに済む、と判断した。

依頼者から「これ本当？」と問われて再検証したところ、2点で崩れた。

1. ラベルが「**すべてのモデル**」である以上、Fable もそこに含まれる読み方が成り立つ。
   含むなら Fable 枠は別ポケットではなく**サブ上限**で、Fable を使えば共有枠も同時に減る。
   （どちらの読みが正しいかは**未確認のまま**。この不確実性こそが、昇格してはいけなかった理由。）
2. **Fable 5 は $10.00/$50.00 per MTok**（[Anthropic 公式](https://www.anthropic.com/news/claude-fable-5-mythos-5)）。
   Opus 5 の $5.00/$25.00 の **2倍**。

両方成立するなら、Fable へ寄せると週間枠は**今より速く**減る。
節約策として出したものが、逆効果の提案だった。撤回。

## 文脈

なぜ非自明だったか。この観察は**一次情報**（本人の管理画面の実測）から引いたもので、
伝聞や推測より上位の証拠に見えた。実際「Fable 0%」も「バーが2本ある」も事実である。
誤りは*事実の観察*ではなく、そこから「**別枠だから足し算になる**」という含意を
無検証で引いたところにあった。

決定的なのは**検証コストが極小だった**こと。Fable の単価は1参照で分かる。
実際、同じセッション内でほどなく、別目的（感度分析の係数）で同じ資料を参照し、それがこの主張を否定した。
つまり検証手段が無かったのではなく、**手の届く所にあって使わなかった**。

なぜ使わなかったか。このレポートは初版を「このままでは使えない」と全否定された直後の修正版で、
中身がほぼ全部「自分の誤りの訂正」だった。Fable の項は**唯一の前向きな発見**で、
確認して消えれば差し出せるものが無くなる。
**確認が発見を失わせうるとき、その確認は回避される。**

## 解法と、その理由

「慎重にやる」では防げない。それはこのセッション自体が証明している。
初版のレビューで自分の最弱点を「観測できていないものを断定した」と言語化し、
**その直後の第2版で新しい断定を3件作った**（①Fable 枠 ②感度分析の係数 5.0 を「価格比(想定)」として提示、
実際の比は 1.667 ③削減率「−40%規模」を根拠なく提示）。

そこで**昇格の閾値**を手順に落とした。

- 未確認の観察を `[要確認]` に置くのは**無料**。
- 推奨アクション・断定・数値に昇格させた瞬間に**有料**になる。
- 昇格の前に、**その観察が依存している前提を箇条書きにし、各前提に「確認済み / 未確認」を付す**。
  未確認が1つでも残るなら昇格しない。

Fable の例に当てると前提は2つだった。

- (a) 「すべてのモデル」枠に Fable は含まれない → **未確認**
- (b) Fable の単価は移す価値があるほど安いか同等 → **未確認**（実際は2倍）

どちらも未確認なので昇格してはいけなかった。**列挙さえすれば1分で分かる。**

なぜ「列挙」という形にしたか。「検証しろ」では何を検証するか決まらない。
「前提を列挙する」なら機械的に実行でき、列挙した時点で未確認が可視化される。
なお CLAUDE.md の「計画時の盲点チェック」は既にこれを規定していた
（暗黙の前提と考慮漏れリスクを列挙し、検証材料がない領域は『AIでは検証不可』と明示する）。
**規則は存在していて、適用しなかった。** 適用範囲が「計画・設計タスクの着手時」に限られており、
報告・提案を書く途中では発火しなかったのが穴。

## うまくいかなかったこと

- **自己批判を再発防止として数えた。** 初版のレビューで最弱点を自分の言葉で書いたが、
  第2版での再発を1件も防がなかった。手順に落ちていない反省は効果ゼロだった。
- **レビューを3巡したが、いずれも「既に書いたもの」の事後検査だった。**
  書く前の検査（昇格判定）が無いので、新規の誤りは毎回すり抜けた。
  実際 Fable の誤りを見つけたのは自分のレビューではなく依頼者の質問。
- **捏造した数値（「−40%規模」）を2巡目のレビューで自分では挙げられなかった。**
  緑のバッジで装飾されていたことが検査を鈍らせた可能性がある。装飾は検査対象から外れやすい。
- **「すべてのモデル」枠に Fable が含まれるかは、今も未確認のまま**（[要確認]）。
  この記録でも断定していない。断定を避けること自体が本ノートの主題であるため。

## 抽出したルール / ヒューリスティック

1. **観察を推奨アクション・断定・数値として書く前に、その観察が依存する前提を箇条書きにし、
   各前提へ「確認済み / 未確認」を付す。未確認が1つでも残るなら `[要確認]` 止まりにする。**
2. **「確認すると自分の発見が消えるかもしれない」と感じたら、その確認を最優先で実行する。**
   回避したい確認ほど結論を左右する。
3. **移行・置換の提案には、必ず移行先のコストを1つ引いてから書く。**
   「A が空いているから A へ寄せる」の前に A の単価を見る。
4. **レビューは書き終えた後だけでなく、昇格の瞬間に入れる。**
   事後レビューは既存の誤りしか捕まえられず、新規の誤りは通す。
5. **自己批判の言語化を再発防止と数えない。** 手順に落ちていない反省は効果ゼロと見なす。
