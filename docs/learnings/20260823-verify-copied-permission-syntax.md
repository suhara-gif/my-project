# SNS発のpermissions設定スニペットは、構文とセッション運用モデルの両方を一次情報で裏取りしてから採用する

- 日付: 2026-08-23
- 種別: 調査 / 失敗した試み
- 触れたファイル: .claude/settings.json, .claude/README.md

## 問題

X（旧Twitter）発のメルカリ社Claude Codeセキュリティ設定の紹介記事を読み、
「取り入れるべき示唆はあるか」と聞かれて回答した。1回目の回答では、記事内の
`permissions` JSONスニペット（`"Bash(curl:)"` 等のdenyリスト、`"ask": ["Bash(git push:)"]`）
を検証せずほぼそのまま「導入して良い」と提案した。

第三者レビューを自分自身にかけたところ、2つの独立した欠陥が見つかった。

1. **構文誤り**: `"Bash(curl:)"`（コロンの後ろにワイルドカード無し）は、公式ドキュメントの
   構文と照合すると「curl」という完全一致・無引数コマンドにしかマッチせず、
   `curl https://...` のような実際の呼び出しを一切ブロックしない。正しくは `Bash(curl:*)`。
   SNS上でアスタリスクがイタリック記法と誤認され欠落したとみられる。
2. **運用モデルの見落とし**: 記事の `"ask": ["Bash(git push:)"]` を、このリポジトリの
   共有・git管理下の `.claude/settings.json` にそのまま入れる提案をしていたが、
   このファイルはリモートセッション（本セッションを含む）にも個人設定を介さず直接効く
   （`install-to.sh` のコメントで実機確認済みと明記されていた）。かつ本セッションの
   `permission_mode` は `auto` で、公式ドキュメント上 `ask` ルールはプロンプトを出せない
   セッションでは実質ブロックとして働きうる。つまり「pushしてタスクを完了する」ことを
   要求されるこのリポジトリの自動化フロー自体を壊しかねない提案だった。

## 文脈

なぜ非自明だったか。1回目の回答は「元記事の主旨（このセキュリティ設定を導入すべきか）」
には正しく答えていたので、一見もっともらしかった。誤りは主旨ではなく**転記したJSONの
細部**（末尾のワイルドカード）と、**設定の適用範囲**（このファイルが今まさに自分自身の
セッションにも効くという事実）にあった。どちらも「読めば書いてある」情報ではなく、
公式ドキュメントへのアクセスと、リポジトリ内の別ファイル（install-to.sh のコメント）・
自セッションのメタデータ（get_session の permission_mode）を突き合わせて初めて見える。

## 解法と、その理由

ユーザーから「第三者レビュアーとして自案を検証し、事実はWeb検索で裏取りせよ」と
明示的に指示され、次の手順を踏んだ。

1. WebFetch/専用エージェントで公式ドキュメント（code.claude.com/docs/en/permissions）
   の該当箇所を**直接引用**で取得し、記事のスニペットと1文字単位で突き合わせた。
2. 「このファイルは誰に効くか」を一般論で語らず、`get_session` ツールで**本セッション
   自身の permission_mode を実測**した。自分が今まさに影響を受ける当事者であることを
   確認してから可否を判断した。
3. 検証で見つかった欠陥を重大順に並べ、生き残った主張（`disableBypassPermissionsMode`
   のキー名・配置は正しかった）も明示して区別した。全否定でも無検証採用でもない。

## うまくいかなかったこと

- 1回目の回答で「エスカレーション規則に抵触しない」と書いたが、これはCLAUDE.mdの
  エスカレーション規則（claude-backup固有の5項目）がそもそもこのケース（Claude Code
  自身のpermissions変更）を想定していないだけであり、「規則に照らして許可と判定した」
  かのように書いたのは根拠のない先回りだった。「規則が対象外」と「規則が許可している」
  は違う。

## 抽出したルール / ヒューリスティック

1. **SNS/ブログ発の設定JSON（permissions・hooks・env等）は、コピー元の書式が崩れている
   前提で扱う。** 特に `*` はMarkdown/SNSのイタリック記法と衝突して欠落しやすい。
   採用前に必ず公式ドキュメントの構文例と1文字単位で突き合わせる。
2. **「この設定は誰に効くか」を一般論で答えず、対象セッション自身のメタデータ
   （`get_session` の `permission_mode` 等）で実測する。** 特に共有・git管理下の
   `.claude/settings.json` は、自分が今実行中のセッションにも遡って効くことがある。
3. **`ask` ルールは「毎回聞かれるだけ」と決めつけない。** プロンプトを出せない
   セッション（headless/auto/dontAsk）では実質 `deny` と同じ結果になりうる、と
   ドキュメントで確認してから採用可否を決める。
